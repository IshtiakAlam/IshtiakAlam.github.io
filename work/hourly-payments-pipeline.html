Payments data every hour instead of once a day

A daily full reload became an incremental hourly job. Finance and risk now see payments within the hour, and each run takes 8 minutes instead of 95.

Role
Designed and built it
Company
Axi
Deployment
Asset Bundles through Azure DevOps CI
Stack
Databricks, Delta Lake, PySpark

The situation

Payments data reached Axi’s lakehouse through a daily job that reloaded the full history on every run. It took 95 minutes, and because it ran once a day, a payment could wait up to 24 hours before finance and risk saw it.

As history grew, so would the run time. The fix wasn’t a bigger cluster. It was to stop reprocessing data that hadn’t changed.

What changed

  1. Read only what changed. Each run picks up rows updated since the last successful run, using a watermark on the last-updated timestamp.
  2. Merge by business key. Changes merge into the Delta table by payment ID, so a rerun updates rows instead of duplicating them.
  3. Run every hour. With a run that small, an hourly schedule costs little and cuts the delay to under an hour.
  4. Ship it as code. The job, its schedule and its compute live in a Databricks Asset Bundle, deployed through Azure DevOps CI like any other change.

Key decisions

  • Watermark on updates, not inserts

    Payments change state after they’re created. Tracking the last-updated time means status changes reach reporting too, not only new payments.

  • Safe to rerun

    Merging on payment ID makes every run idempotent, so a failed hour can simply run again.

  • Hourly batch, not streaming

    Finance and risk needed numbers within the hour, not by the second. An hourly batch met that with far less to operate than a streaming job.

  • Job settings in the repository

    With Asset Bundles, schedule and cluster changes go through pull requests instead of being edited by hand in the workspace.

If you’re making the same change

  • Check the source can tell you what changed. Incremental loads need a reliable updated-at column or change feed. Confirm it exists before designing around it.
  • Re-read a small overlap. Late updates can land just behind the watermark. Re-reading the last few minutes on each run is cheap insurance.
  • Keep a full reload for recovery. A backfill job that rebuilds history is still worth having. It just shouldn’t be the daily path.
